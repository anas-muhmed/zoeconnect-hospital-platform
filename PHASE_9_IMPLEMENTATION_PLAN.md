## Pre-flight

The target topology was not an open question — `HDSP_Cloud_Migration_Architecture_Review.md` (written earlier in this project, before Phase 9 began) already recommends ECS Fargate over Kubernetes/Cloud Run specifically because it "maps cleanly onto the existing three-process model (API, worker, Next.js ≈ current PM2 `apps` array)" and integrates natively with Secrets Manager, ALB host-based routing, and CloudWatch Logs. That review is also where the roadmap's Task 9.2/9.6 "prior review Section 13/Section 10" references resolve to (the roadmap's own Section numbering points into this document, not `HDSP_Hybrid_Deployment_Architecture_Review.md`, which was checked first and found to reference something else — a self-hosted/cloud licensing comparison, not the cloud worker architecture). Existing self-hosted infra (`DEPLOY.md`, `infrastructure/pm2/ecosystem.config.js`, `infrastructure/docker-compose.yml`) was read first so cloud deployment doesn't silently diverge from documented self-hosted behavior where the two should match.

**A real gap found and fixed before it could bite a real deployment:** the prior review explicitly flags "in-process cron/`setInterval` schedulers — a second replica would double-process every tick with no distributed lock; must move to a single designated worker service... before horizontal scaling of the worker tier." The existing self-hosted PM2 config already runs 2 cluster instances of the same combined process — meaning this risk technically already exists today, latent, at small scale. Phase 9's `PROCESS_ROLE` split (Task 9.6) directly closes it for the cloud target: an `api`-role process never imports `ScheduleModule`, so scaling the API tier to N tasks is safe by construction. Bull queue *consumers* are a separate, lower-severity case — Bull's own per-job Redis lock already makes concurrent consumption across replicas safe (that's what queues are for), so co-locating Bull processors in both roles for now is a resource-efficiency question, not a correctness bug — documented as a follow-up, not silently left unexamined.

**A second real gap found while wiring RDS/ElastiCache Terraform:** the roadmap's Task 9.3 text claims "connection details wired through existing `database.config.ts`/`redis.config.ts` — no code change needed." True for Postgres. False for Redis once ElastiCache's `transit_encryption_enabled` (TLS) is turned on — `ioredis`'s object-style config (host/port/password, as used in `redis.config.ts`/`RedisProvider`/`bullAsyncOptions`) does not auto-negotiate TLS the way a `rediss://` URL does; it needs an explicit `tls` option. Fixed with a small, additive `REDIS_TLS` env var (default `false`, self-hosted unaffected) rather than silently shipping Terraform that would fail to connect, or silently disabling ElastiCache's encryption-in-transit to dodge the code change.

## Task sequencing

1. **Task 9.6 — `PROCESS_ROLE` split** (done first, out of roadmap's listed order, because Task 9.2's task definitions needed it defined to reference correctly): `app.config.ts` gains `processRole` (`all`/`api`/`worker`, default `all`) and `logToStdout`. `app.module.ts` conditionally omits `ScheduleModule.forRoot()` when `PROCESS_ROLE=api`. `main.ts` conditionally calls `app.init()` instead of `app.listen()` when `PROCESS_ROLE=worker` — every lifecycle hook (DB/Redis connections, Bull queue registration) still runs, just no HTTP port opens for an ALB to accidentally route to. Self-hosted (`PROCESS_ROLE` unset, defaults `'all'`) is byte-identical to pre-Phase-9 behavior.
2. **Task 9.1 — Dockerfiles** (`infrastructure/docker/{backend,frontend,connector}.Dockerfile`): multi-stage builds, monorepo-root build context (required — backend/frontend/connector all depend on local `file:` workspace packages that must be built to `dist/` before `npm ci` can resolve them). Backend/worker share one image (`backend.Dockerfile`, distinguished only by `PROCESS_ROLE`/CMD) and deliberately do NOT bundle Oracle Instant Client — Task 9.8's target config (`ORACLE_TRANSPORT=cloud_relay`) means the backend never dials Oracle directly. The Connector image DOES bundle it (it's the one component dialing Oracle directly, at the hospital edge) — Instant Client itself can't be redistributed via a public base image per Oracle's license, so it must be staged into the build context manually, documented rather than faked.
3. **Task 9.2 — ECS Fargate task definitions/services**: `infrastructure/ecs/*.json` (human-readable, heavily-annotated reference versions) plus `infrastructure/terraform/ecs.tf` (the actual Terraform-managed source of truth — kept separate rather than templating one from the other, since the JSON files' explanatory `_comment`/`_note` fields aren't valid ECS schema and would need a fragile stripping step to reuse directly). Three core services (API, worker, frontend) sized per the "Small (pilot)" tier from `HDSP_Cloud_Migration_Architecture_Review.md` Section 17 (2/1/2 tasks). A fourth, optional `connector-task-definition.json` is provided but not Terraform-managed — Connector deployment ownership is explicitly Phase 10's decision, per Phase 7's Vendor Portal impact analysis.
4. **Task 9.3 — RDS Postgres (Multi-AZ) + ElastiCache Redis** (`rds.tf`, `elasticache.tf`): sizes/settings per the pilot tier, generated passwords/auth tokens via `random_password`, flowing into Secrets Manager (`secrets.tf`) rather than Terraform literals. Surfaced and fixed the Redis-TLS application-code gap described above.
5. **Task 9.4 — S3 + CloudFront** (`s3.tf`, `cloudfront.tf`): private bucket (blocked public access, matching `S3StorageProvider`'s existing presigned-URL access pattern, Phase 3), CloudFront with Origin Access Control provisioned for future CDN-fronted delivery of public assets — explicitly not wired into application code this phase, since `S3StorageProvider` doesn't currently emit CloudFront URLs and changing that would be an application code change beyond this phase's stated scope.
6. **Task 9.5 — ALB host-based routing + WAF** (`alb.tf`, `waf.tf`): one wildcard host rule (`*.${CLOUD_BASE_DOMAIN}`) split by path (`/api/*` → API target group, everything else → frontend target group) — HDSP is single-app multi-tenant (tenant resolution happens inside the app via `SubdomainTenantMiddleware`, Phase 8), not per-tenant ALB rules; a genuinely per-tenant routing tier would only apply to a future dedicated-isolation deployment tier, out of scope here. WAF: three AWS managed rule groups (Common, Known Bad Inputs, SQLi) plus a coarse IP-based rate limit — an infrastructure-level backstop, not a replacement for the application's own per-account throttle config.
7. **Task 9.7 — CloudWatch logging + health checks**: `logger.util.ts` gains `LOG_TO_STDOUT` (forces Winston's console transport on in production, and skips the now-pointless rotating file transports, since ECS Fargate's filesystem is ephemeral and CloudWatch's `awslogs` driver only captures stdout/stderr, not files). Self-hosted (`LOG_TO_STDOUT` unset) is unaffected — file transports stay exactly as before. Health checks needed no new code — `@nestjs/terminus`'s existing `/api/health`/`/api/health/live` endpoints (already "cloud-ready" per the roadmap's own framing) are referenced directly by the ALB target group health check and the API/frontend ECS task definitions' container health checks. The worker service has neither (no HTTP listener to probe, per Task 9.6) — documented as container-status-based liveness instead of inventing an HTTP endpoint solely for this.
8. **Task 9.8 — `DEPLOYMENT_MODE=cloud` runbook**: `CLOUD_DEPLOY.md`, mirroring `DEPLOY.md`'s style and section structure. Documents the full four-provider-plus-deployment-mode flip as pure configuration (no code changes needed for any of the four provider selections — that is the entire point of Phases 3-8's abstraction work), staged staging-first per the roadmap's explicit instruction.

**Follow-ups for a human:**
1. **Never applied against a real AWS account** — no credentials or account exist in this sandbox. `terraform validate` and a real `plan`/`apply` against a non-production account are required before trusting this for a staging cutover. Same posture as every other environment-dependent item in this project (B9-B12, Phase 6/7's real-Oracle checks).
2. Bull queue processors are not yet excluded from the API-role module graph — only cron (`ScheduleModule`) is gated by `PROCESS_ROLE`. Safe today (Bull's per-job Redis lock makes concurrent consumption across API+worker replicas correct, not a bug), but a further optimization to move `@Processor()` classes into a worker-only module subset would let the API tier be purely request-focused. Not attempted this phase — real module-graph surgery across many feature modules, higher risk than warranted without real test infrastructure to verify against.
3. CloudFront is provisioned but unused by application code — `S3StorageProvider` still serves via presigned S3 URLs. Wiring CDN URLs through would be a Phase 3-adjacent application code change, out of this phase's "infrastructure only" scope.
4. Connector deployment mechanism/ownership remains Phase 10's open decision (carried forward again from Phase 7's Vendor Portal analysis) — `infrastructure/ecs/connector-task-definition.json` exists as one option, not a resolved answer.
5. DR drill (simulated AZ failure), load test at expected initial scale, and a full re-run of every prior phase's testing checklist against a real staging environment — all explicitly named in the roadmap's own Task 9 testing checklist, none executable in this sandbox.
6. `LICENSE_PUBLIC_KEY_PATH` has no Secrets Manager entry in this pass, since Task 9.8's target config uses `LICENSE_PROVIDER_MODE=subscription` (DB-backed, no RSA key file needed) — only relevant if a future cloud deployment ever runs `LICENSE_PROVIDER_MODE=file`.
