# Tenant-Scoped User Identity — Implementation Plan

**Companion to:** `TENANT_SCOPED_IDENTITY_AUDIT.md` (the findings this plan fixes) and `OWNERSHIP_MODEL_AUDIT.md` (the related, separate ownership review). Follows this project's standard phase-doc pattern (see `PHASE_8_IMPLEMENTATION_PLAN.md`'s log-only/enforced staged-rollout precedent, reused directly below for the highest-risk step).

**Status: plan only. Nothing in this document has been implemented.** Each task below is scoped to be independently reviewable and shippable; sequencing exists to keep the platform working correctly at every intermediate step, not to force one giant cutover.

## Decisions locked (2026-07-17, user-confirmed)

The pre-flight question this plan originally posed as open has been decided. Recorded here verbatim in spirit, not re-litigated below:

1. **Login strategy: Option A, subdomain-required login — confirmed, not just recommended.** Tenant is resolved from the `Host` header before username/password are ever evaluated: `Tenant → Username → Password`, not `Username → search every tenant → guess`. Reuses `SubdomainTenantMiddleware` exactly as built; no tenant-picker UI, no username enumeration, no extra screen; self-hosted continues resolving to `'default'` unchanged. Option B (tenant-picker) is off the table unless a future central-login-portal product need reopens it — not anticipated, not designed for here. Option C is superseded: **email is also being tenant-scoped**, not kept global (see item 6 below), so the login redesign covers both identifiers uniformly.
2. **Task order changed** from the original 2→4→1→3→5 to **1 → 2 → 4 → 6 → 3 → 5 → 7 → 9 → 8 → 10**. Rationale: data hygiene (1) must precede *any* uniqueness work, including Task 2's `hisEmployeeCode` index, not just Task 5's composite constraints — a stray `NULL`-tenant row could defeat Task 2's partial unique index the same way it would Task 5's. Task 6 (role/permission assignment validation) is tiny, fully isolated, and a free win to clear out of the way before touching anything login-related.
3. **Shadow mode confirmed as non-negotiable** — authentication behavior is never changed directly; every change to `login()`/`forgotPassword()` goes `LOG ONLY → observe → ENFORCED`, exactly the `TenantScopeGuard` precedent this plan already cited.
4. **`tenant_id NOT NULL` is now an explicit, required step**, not an optional hardening decision deferred to "someday." Folded into Task 5 below — every tenant-owned table this migration touches gets a hard `NOT NULL` constraint on `tenant_id` after backfill, specifically to prevent a future `INSERT ... tenant_id = NULL` from silently reopening the exact hole this plan closes. "Effectively non-null" was the wrong bar; "cannot be null" is the actual requirement.
5. **`hisEmployeeCode` priority reaffirmed.** Correctly identified as the biggest live correctness bug, since HIS-based login bypasses `username` entirely. The partial composite index specified in Task 2 (`UNIQUE (tenant_id, his_employee_code) WHERE his_employee_code IS NOT NULL`) is confirmed as the exact right shape, unchanged.
6. **`email` is now tenant-scoped, not kept globally unique.** Superseding original Option C: hospital software legitimately has repeated generic addresses across tenants (`admin@hospital.local`, `it@hospital.local`, shared test addresses like `admin@gmail.com`), so a global email constraint would be an unnecessary restriction, not a safety feature, in this domain. Task 5's composite-constraint list already included `UNIQUE (tenant_id, email)` — no schema change needed from the original plan, just confirming this was the right call and is not being walked back to global.
7. **Task 9's pre-flight scope widened.** Not just a subdomain/username check — Vendor Portal should pre-flight **subdomain, username, email, and HIS code (if supplied)** before provisioning begins, so a collision on any of the four fails fast instead of after five other resources are already committed. Task 9 below is updated accordingly.
8. **JWT tenant identity — verified already satisfied, not a new task.** `JwtPayload` has carried `tenantId`/`tenantSlug` since Phase 8 Task 8.1 (`jwt.strategy.ts:12-51`), set at issuance in `AuthService.generateTokens()` from `user.tenantId` (`auth.service.ts:535-560`), and `TenantScopeGuard` (Task 8.3) already cross-checks `payload.tenantId` against `req.tenantId` on every non-`@Public()` route. Every authorization decision after login already has tenant available without a second lookup, exactly as required. The one real gap was never the JWT's shape — it was that `login()` itself never *consulted* `req.tenantId` when finding the user in the first place, which is precisely what Task 3 (login redesign) fixes. No new task added for this; it's recorded here as a confirmed precondition so it isn't mistakenly re-implemented.

## Task sequencing

### Task 1 — Data hygiene precondition: verify no `User`/`Role` row has a `NULL` `tenant_id`

**Why first:** Postgres treats `NULL` as distinct from every other `NULL` in a unique index, so a composite `UNIQUE(tenant_id, username)` constraint would silently fail to prevent duplicates among any rows still carrying `tenant_id: NULL` — the exact legacy-seed-script gap the ownership-model audit already flagged (`seed-platform.ts` inserts rows without a `tenant_id` column at all). This must be closed before Task 5's constraint change, or the new constraint would be a no-op for exactly the rows most likely to collide (dev/legacy installs).

- Write a migration-time verification query (not a schema change) that counts `users`/`roles` rows with `tenant_id IS NULL`, run against every environment this migration will touch before Task 5 proceeds.
- For any found: backfill to the seeded `'default'` tenant's real UUID, using the exact same equivalence logic `AuthService.isSetupRequired()`/`setupSuperAdmin()` already established in Phase 8 (Task 8.4) — don't invent a second backfill convention.
- Fix `seed-platform.ts` itself to stamp `tenant_id` on the rows it inserts, so this gap can't reopen on the next fresh dev seed.
- **Risk:** low — read-only verification plus a backfill pattern already proven safe in Phase 8 and in the earlier Users-module tenant-scoping fix.
- **Blocks:** Task 5.

### Task 2 — `hisEmployeeCode`: add tenant-scoped uniqueness and fix the lookup (do this first among the "real fixes" — most contained, highest severity)

This is the single most urgent item in the audit — it has no uniqueness constraint at all today, tenant-scoped or global, and already backs a live auto-login path (`hisLogin()`). It's also fully self-contained: fixing it doesn't depend on the login-flow decision above, since HIS-integrated login already has implicit tenant context (the request originates from a specific hospital's Oracle instance/subdomain).

- Migration: add a **partial** unique index `UNIQUE (tenant_id, his_employee_code) WHERE his_employee_code IS NOT NULL` on `users` (partial, since the column is nullable and most users won't have one).
- `UsersService.findByHisEmployeeCode()` (`users.service.ts:112-118`): add a required `tenantId` parameter, add it to the `where` clause.
- Update both call sites: `AuthService.hisLogin()` (`auth.service.ts:157-163`) — pass `req.tenantId`, threading it through from the controller the same way Task 8.4 already threads `req.tenantId` into `setupSuperAdmin()`. `HisController.getUserContext()` (`his.controller.ts:163`) — same.
- **Risk:** low-medium. The partial unique index could fail to create if any tenant already has two users sharing a `hisEmployeeCode` today (possible, since nothing has ever prevented it) — run a pre-migration duplicate check, same shape as Task 1's, and resolve any hits manually before the index is added.
- **Independent of Task 1's `NULL` concern being fully resolved for `username`/`email`**, but still needs its own duplicate check against `NULL` `tenant_id` rows.

### Task 3 — Login-flow redesign, shadow mode first (the linchpin)

This is the task the rest of the plan depends on, and the one place a straightforward "just add tenant_id to the query" change would be unsafe to ship directly, since it changes authentication behavior. Mirrors Phase 8 Task 8.3's `TenantScopeGuard` log-only/enforced staged rollout exactly, for the same reason: give the change a real observation window before it can reject or misroute a real login.

1. `AuthController.login()`: pass `req.tenantId` into `AuthService.login()` (currently not passed at all).
2. `AuthService.login()`: **shadow mode first** — keep the existing global `username`-only lookup as the actual behavior, but additionally run a tenant-scoped lookup in parallel and log (never throw) whenever the two would disagree — i.e., whenever a `(tenantId, username)` match exists but differs from the global match, or doesn't exist at all while the global one does. This produces real production evidence of how many logins would actually be affected, before anything can break a real user's login. Same log-only/enforced env-var pattern as `TENANT_SCOPE_GUARD_MODE` (Task 8.3) — call it `LOGIN_TENANT_SCOPE_MODE`, default `log-only`.
3. Apply the identical shadow-mode treatment to `PasswordResetService.forgotPassword()` (`password-reset.service.ts:80-83`) — same ambiguity class, same silent-failure risk if done wrong (a wrong-tenant password reset is worse than a wrong-tenant login, since it's not immediately visible to the affected user).
4. After a real observation window with `log-only` producing zero or explained mismatches, flip both to `enforced` — at which point the lookup actually adds `tenantId` to its `where` clause and Task 5's schema change becomes safe to ship.
5. **`hisLogin()` is already covered by Task 2** — no separate work needed here, but note the two tasks converge on the same `req.tenantId`-threading pattern.

**Risk:** medium — this is a real, if carefully staged, change to the authentication path. The shadow-mode step is the specific mechanism that keeps it low-risk in practice; skipping straight to `enforced` is not recommended regardless of how confident the analysis looks in this document.

**Blocks:** Task 5 (the DB constraint shouldn't go composite until login is provably tenant-aware in front of it).

### Task 4 — Fix Category B call sites (tenant-context-available-but-unused duplicate checks)

These can ship independently of Tasks 2/3/5, in any order, since adding a tenant filter to a duplicate-check query is a strict improvement even while the underlying DB constraint is still global for now — it just means the app-level check becomes accurate sooner than the DB-level one, with no downside.

- `UsersService.create()` (`users.service.ts:152-158`): add `tenantId` to the duplicate-check `where` clause, using the `tenantId` already resolved two lines later (move that resolution earlier).
- `UsersService.update()` (`users.service.ts:195-198`, `200-203`): same, using the tenant context already established via the tenant-scoped `findOne(id)` two lines above.
- `AuthService.setupSuperAdmin()` (`auth.service.ts:666-678`): add `tenantId` (the `stampedTenantId` computed a few lines below, moved earlier) to the duplicate-check — this directly closes the gap that caused the original incident, and brings the method in line with its own sibling `isSetupRequired()`, which has been tenant-scoped since Phase 8.
- `RolesService.create()`/`update()` (`roles.service.ts:67`, `:101`): same pattern for `Role.name`.
- **Side effect fixed for free:** the 409 error-message information leak flagged in the audit (an admin in Tenant A learning a username exists in Tenant B) disappears automatically once these checks are tenant-scoped, since a colliding username in a different tenant will simply no longer register as a conflict.
- **Risk:** none — additive filtering on an existing query, no schema dependency, safe to ship first if a quick win is wanted before the bigger login-flow work.

### Task 5 — Schema migration: composite unique constraints

Sequenced after Tasks 1, 2, and 3 (shadow-mode-proven-then-enforced) — by the time this lands, the login path is already tenant-aware and tested, `hisEmployeeCode` already has its own constraint, and no `NULL`-tenant rows remain to silently defeat the new index.

- Drop `uq_users_username`, `uq_users_email`, `uq_roles_name`.
- Add composite unique indexes: `UNIQUE (tenant_id, username)`, `UNIQUE (tenant_id, email)` on `users`; `UNIQUE (tenant_id, name)` on `roles`. Email is tenant-scoped here, not kept global — confirmed decision, see "Decisions locked" item 6 above.
- **`tenant_id NOT NULL` — now a required step in this task, not deferred.** After Task 1's backfill guarantees zero `NULL` rows, add a hard `NOT NULL` constraint on `tenant_id` for `users` and `roles` (and, as a matter of consistency, any other tenant-owned table this migration pass touches). This is what actually closes the hole — a composite unique index alone doesn't stop a future `INSERT ... tenant_id = NULL` from being written and silently evading the constraint (Postgres unique indexes treat every `NULL` as distinct); only `NOT NULL` does that. Sequenced strictly after Task 1's backfill completes, in the same migration as the composite indexes so the two can't drift apart in time.
- Fix `seed-platform.ts`'s `ON CONFLICT ("username")` raw SQL to name the new constraint's actual columns (Postgres requires this to match exactly, or the seed script will start failing loudly — a good, cheap safety net that Task 1 already addressed at the data level).
- **Risk:** low by this point in the sequence — the risk this task would otherwise carry (silent constraint no-op, login breaking, mid-provisioning collisions) has already been retired by Tasks 1-3. The only remaining risk is a standard "does this migration run cleanly against every real environment's current data" check, same as any schema migration, plus confirming the `NOT NULL` addition doesn't fail against any environment Task 1's backfill didn't actually reach.

### Task 6 — `resolveRoles()`/`assignPermissions()` tenant validation

Independent of every other task — ships whenever convenient, ideally alongside Task 4 since it's the same root cause (an ID/name lookup that never learned about tenant scoping) in the same service file.

- `UsersService.resolveRoles()` (`users.service.ts:291-298`): add a tenant filter to `roleRepo.find({ where: { id: In(roleIds) } })`, rejecting (not silently dropping) any submitted role ID that doesn't belong to the caller's tenant.
- `UsersService.assignPermissions()` (`users.service.ts:121-145`): confirm whether `Permission` is meant to stay a legitimately global/system table (per the ownership-model audit's classification) — if so, no tenant filter is needed here and this should be documented as a deliberate exception, not silently left inconsistent with `resolveRoles()`.
- **Risk:** low — a validation-tightening change; the only behavior change is rejecting a request that was already semantically wrong (cross-tenant role assignment), not narrowing anything that worked correctly before.

### Task 7 — Vendor-portal-tooling call sites: product decision, then fix

`account-lock-management.service.ts` (`unlockUser()`, `resetAttempts()`, `createUser()`) and `password-reset.service.ts`'s `applyRemoteReset()` all have a UUID-or-username fallback with zero tenant awareness, used by Vendor Portal's remote support tooling.

- **Decision needed:** should vendor-support tooling be allowed to act by username at all in a multi-tenant deployment, or should it be restricted to UUID-only lookups (forcing the vendor operator to resolve the target user's ID through a tenant-scoped admin view first)? This is a smaller, more contained version of the pre-flight decision in Task 3 — recommend restricting to UUID-only for any single command that can mutate an account (`createUser`, password reset, unlock), since these are lower-frequency operator actions where an extra UUID-lookup step is a reasonable cost for removing the ambiguity entirely, rather than trying to make a username fallback tenant-aware.
- If username fallback is kept for read-only or low-risk cases, thread `tenantId` through the same way as Task 4.
- `account-lock-management.service.ts:createUser()` also currently never stamps `tenantId` on the row it creates at all — fix this regardless of the above decision, since it's a correctness gap independent of the uniqueness question.
- **Risk:** low — self-hosted-instance-scoped tooling, smaller blast radius than the main login/creation paths, and not on the critical path for Tasks 1-5.

### Task 8 — HIS webhook contract: add tenant identifier

`HisConfigService.applyHdspUsers()` (`his-config.service.ts:139`) can't be fixed by a query change alone — its payload (`{username, passwordHash, role, fullName, isActive}[]`) has no tenant field at all, so the query has nothing to filter by even if it wanted to.

- Requires coordinating a webhook-contract change with whatever system originates these calls (the vendor-portal-triggered HIS bootstrap/sync path) — add a `tenantId`/`tenantCode` field to the payload shape.
- Once the payload carries tenant identity, update the upsert lookup (`his-config.service.ts:139`) to filter by it, and stop synthesizing `${username}@hdsp.local` email addresses without a tenant-qualified username to build them from.
- **Risk:** medium — the only task in this plan with a cross-system dependency outside this repo's direct control (the actual webhook sender lives in the vendor/HIS integration layer, not purely in this codebase). Sequence this whenever that coordination is realistically available; it doesn't block anything else in this plan and nothing else blocks it.

### Task 9 — Vendor Portal: full pre-flight collision check (subdomain + username + email + HIS code)

Currently, Vendor Portal only pre-checks subdomain collision before calling HDSP's provisioning pipeline; a username collision surfaces five steps later, after a tenant row, subdomain reservation, storage namespace, connector pairing key, and trial license are already committed. **Widened scope per user decision:** the pre-flight check should cover every identifier the provisioning form actually collects, not just username — subdomain, username, email, and HIS employee code (if supplied at provisioning time) — so a collision on any one of them fails fast, before any resource is committed, rather than fixing only the specific field that happened to cause the original incident.

- Add a new, narrowly-scoped HDSP endpoint (tenant-aware, e.g. `POST /platform/tenant-provisioning/check-availability` accepting `{ subdomain, username, email, hisEmployeeCode? }` and returning per-field availability) that Vendor Portal's `CloudTenantsService.provision()` calls before committing step 1, extending the existing subdomain-only pre-check it already does rather than replacing it.
- This is a genuine improvement regardless of whether identifiers stay globally unique (pre-Task 5) or become tenant-scoped (post-Task 5) — it turns a mid-pipeline failure into a fast, pre-flight one either way, and is safe to ship independently and even ahead of the rest of this plan if a quick operational win is wanted.
- **Risk:** low — additive, new endpoint, no existing behavior changed.

### Task 10 — Broader sweep of other global `unique: true` columns

The schema audit flagged several other columns with the same shape of risk, not individually traced in this pass: `CardCategory`, `DisplayPage.name`, `TokenKiosk.kioskSlug`, `SystemSetting.settingKey`, `FeedbackQrCode.token`, `HisSchemaConfig.configKey`.

- Treat as a smaller, separate follow-on audit — for each, determine (same methodology as this whole review) whether it's a genuine tenant-scoped identity the same way `username` is, or a value that's actually fine to stay global (e.g. `FeedbackQrCode.token` is a random opaque token, globally unique by design and correctly so, not a "same value legitimately used by two tenants" situation like `username`).
- **Not blocking, not urgent** — flagged so it doesn't get lost, but nothing in the audit found evidence any of these are actively causing incidents the way `username`/`hisEmployeeCode` already have.

**Implemented so far:** All ten tasks (1, 2, 4, 6, 3, 5, 7, 9, 8, 10 — all 2026-07-17/18). See `HYBRID_ARCHITECTURE_LOG.md` for implementation notes. This plan is now closed.

**Task 10 implementation note — split into three outcomes, not one fix applied uniformly.** Pre-flight research (this task's own dedicated investigation) read all six flagged columns' actual entity code, not just their names, and found the plan's own framing ("determine whether it's a genuine tenant-scoped identity... or fine to stay global") already had three different answers baked into the codebase's existing doc comments, not two: (1) `FeedbackQrCode.token` — confirmed correctly global (the plan's own cited example, a random opaque token). (2) `CardCategory.code` and `DisplayPage.slug` — each entity's own Stage-B-era doc comment explicitly states tenant-ownership is an *undecided, open* architectural question, not a bug ("Whether card categories end up tenant-owned or remain shared/global config is an open architectural question, not decided by this column's presence"). Left untouched — resolving an explicitly-flagged open product decision unilaterally is out of scope for a "not blocking, not urgent" sweep. (3) `SystemSetting.settingKey` — its own comment plus a separate, explicit "DOCUMENTED REINTERPRETATION" note already in `TenantProvisioningService` declare this table a deliberate platform-wide global singleton, with per-tenant rows out of scope by design (`PHASE_10_DEFERRED_BACKLOG.md`). This is an *already-made* decision, not an open one — respected, not overridden. Only `TokenKiosk.kioskSlug` and `HisSchemaConfig.configKey` were genuine, unhedged tenant-scoped-identity gaps (the same shape `username` was before Task 5) and got the full Task-5-style fix: composite `(tenantId, key)` unique constraint, `tenantId NOT NULL`, backfill migration (`1783890000000-Task10TenantScopedUniqueConstraints.ts`). `TokenKioskService.createKiosk()` already stamped `tenantId` (from earlier Stage B work) and now guards against the rare null-context case instead of hitting a raw DB error. `HisConfigService.applyWebhookUpdate()` (a second, older write path into the same table Task 8's `applyHdspUsers()` already fixed) now reuses that same `resolveTargetTenant()` bridge, and `LicenseController.vendorWebhook()` threads `dto.tenantId` into it too. One residual gap deliberately left open and documented, not silently missed: `HisConfigService.getConfig()`/`loadFromDb()`'s Redis cache is still tenant-unaware (one flat map under one global key) even though the underlying table is now tenant-scoped — safe today because self-hosted has one tenant, but would mix tenants' Oracle mappings the moment a real multi-tenant cloud HIS-sync path is built. Flagged in the service's own class-level doc comment for whoever builds that path.

**Task 8 implementation note — confirmed latent risk, not a live incident; shipped as a forward-compatible, backward-safe contract change.** Pre-flight research (this task's own dedicated investigation) established two things not visible from the write-up alone. First, `LicenseController.vendorWebhook()` is the *only* caller of `applyHdspUsers()` — it lives in the same `HIS_CONFIG_UPDATE` branch that also calls `applyWebhookUpdate()`, guarded by manual HMAC-SHA256 verification (`X-Vendor-Signature`, keyed by a per-hospital `instanceSecret`), not `SubdomainTenantMiddleware`/JWT — so `req.tenantId` was never usable here (self-hosted webhook deliveries hit a bare `publicIp:publicPort` URL, which `extractSubdomain()` always fails to resolve to a subdomain, falling back to 'default' regardless). Second, and more importantly: the sender that actually exists in this repo, `HospitalsService.pushHisConfigWithUsers()` in `vendor-portal/backend`, only ever targets the self-hosted `Hospital` entity — confirmed via `CLOUD_TENANT_ONBOARDING_DESIGN.md`'s own documented topology ("self-hosted and cloud are built and deployed as separate images," "self-hosted has exactly one tenant, seeded once") and a direct grep of `cloud-tenants/` module finding zero references to `WebhookService`/`deliver()`/`hdspUsers` anywhere. `CloudTenant` (the multi-tenant SaaS entity) has no HIS-sync feature built at all yet, and `WebhookService.deliver()`'s signature is nominally typed to `Hospital` specifically. **So the mis-tenanting risk this task closes is real but currently latent** — every self-hosted deployment already has exactly one tenant, so stamping to 'default' was already the correct end state for the only live caller; the risk is that a future cloud HIS-sync feature would inherit this same code path and silently mis-tenant users the moment it's built, with no payload field available to prevent it. Implementation: `VendorWebhookDto` gained an optional `tenantId` (UUID, validated with `@IsUUID()`), threaded from `LicenseController.vendorWebhook()` into `HisConfigService.applyHdspUsers(users, tenantId?)`. A new `resolveTargetTenant()` helper resolves either the supplied `tenantId` (validated against the real `Tenant` table — an unresolvable UUID aborts the whole batch rather than silently falling back to 'default', since a silent fallback on a bad tenant UUID would be worse than failing loudly) or the seeded 'default' tenant, unchanged from pre-Task-8 behavior when `tenantId` is omitted. The existing-user upsert lookup, previously `{ username }` alone, is now `{ username, tenantId: targetTenant.id }` — required by Task 5's composite `(tenantId, username)` uniqueness, since a bare username lookup could otherwise find and silently overwrite a different tenant's user with the same username. New-user placeholder emails stay exactly `${username}@hdsp.local` for the 'default'-tenant path (self-hosted, the only live caller — deliberately not changed, to avoid altering production email values for zero benefit), and become `${username}@${tenantCode}.hdsp.local` only when a real non-default `tenantId` is supplied. No Vendor Portal-side sender change was made in this pass, since none exists yet to update — this closes the contract gap pre-emptively so a future `CloudTenant`-facing HIS-sync feature has `CloudTenant.hdspTenantId` (confirmed to be the stable, already-known identifier — `CloudTenant.hdspTenantId === Tenant.id`) ready to pass through from day one, rather than needing a second contract change later.

**Task 9 implementation note.** Shipped with one deliberate departure from the literal write-up: `hisEmployeeCode` is accepted by the new endpoint's DTO (per the plan's explicit naming of it) but Vendor Portal's own `provision()` never actually sends one, since its provisioning form has no such field and a new tenant's SUPER_ADMIN is never created with an `hisEmployeeCode` at provisioning time in the current flow (HIS mapping happens later, out of scope here). More significantly: Task 5 (composite tenant-scoped uniqueness, shipped earlier in this same session) changed the ground truth this task's write-up assumed -- `username`/`email` are no longer globally unique, so a pre-flight "is this username taken" check can no longer be a real collision check the way `subdomain` still is. The new endpoint reports `subdomain` as `blocking: true` (genuine collision) and `adminUsername`/`adminEmail`/`hisEmployeeCode` as `blocking: false` advisory notes (informational only, never rejects a request). See `TenantProvisioningService.checkAvailability()`'s doc comment for the full reasoning.

**Task 7 implementation note.** The plan's "decision needed" was resolved in favor of the option this document itself recommended: account-mutating vendor commands (`unlockUser()`, `resetAttempts()`, `applyRemoteReset()`) now require a UUID target identifier, with the username fallback removed entirely rather than made tenant-aware -- `createUser()`'s own tenantId gap was already closed in Task 5 (it's a create, not a lookup, so the UUID-vs-username question doesn't apply to it the same way). Vendor operators resolve a target user's UUID via `getLockedUsers()` (already returns `user.id`, deliberately left cross-tenant/unscoped -- it's a vendor-wide support view, not a per-tenant admin panel, so this is correct as-is, not a gap).

**Task 5 implementation note — a real bug in Task 6 was found and fixed as a required companion change.** Making `roles.tenant_id` `NOT NULL` (this task) turned Task 6's `tenantId: IsNull()` global-role fallback into permanently dead code, since Task 1's backfill had already converted every `NULL`-tenant `roles` row to the seeded 'default' tenant's real UUID — meaning any tenant other than 'default' assigning a shared system role (SUPER_ADMIN, HOSPITAL_ADMIN) via `UsersService.resolveRoles()` would incorrectly get "Role(s) not found." `Role` is confirmed (via `TenantProvisioningService.stepEnsureGlobalRoles()`'s own doc comment and `seed-platform.ts`) to be a genuinely global, single shared catalog, not a per-tenant resource — every tenant's users point at the exact same `Role` rows. `resolveRoles()`'s fallback was widened to match the seeded 'default' tenant's real UUID instead of `NULL`, mirroring the same "null-vs-default equivalence" pattern `AuthService.isSetupRequired()` already used. This is the first concrete instance of the exact gap `PHASE_10_DEFERRED_BACKLOG.md` item 7 already flagged ("needs the same tenant-or-global fallback `isSetupRequired()` already proves out").

**Task 3 implementation note — three-state mode, not the two-state `log-only`/`enforced` shape originally specified above.** Per explicit user direction, `LOGIN_TENANT_SCOPE_MODE` ships as `legacy` | `shadow` | `enforced` rather than this plan's original `log-only`/`enforced` pair — `legacy` is a true no-op emergency-rollback value (byte-identical to pre-Task-3 behavior, zero tenant-aware query ever runs), which the two-state design didn't have. `shadow` is this document's `log-only` under a new name. Default is `shadow`. `PasswordResetService.forgotPassword()` (item 3 in the Task 3 write-up above) was **not** touched in this pass — scope was the login path only (`AuthService.login()`/`AuthController.login()`/`widgetLogin()`); the password-reset shadow-mode treatment remains open and should be picked up as a follow-on before Task 5 enforces the composite constraints, since it shares the same ambiguity class called out above.
