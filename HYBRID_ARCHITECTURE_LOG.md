# Hybrid Architecture Implementation Log

Delivery journal for the Hybrid Architecture roadmap (`hybrid-architecture` branch) — Phase 0 (deployment-mode scaffolding) and Phase 1 (Tenant Foundation, Stage A: additive/nullable `tenant_id` migration across ~110 entities, batched into checkpoints A1–A13). Stage B (`NOT NULL`, FK, composite constraints, repository-level tenant filtering) is explicitly deferred and not covered by any entry below.

## Checkpoint A5.5 — API Contract Audit (2026-07-14)

**Trigger:** A live regression was found after A5 — `PATCH /api/v1/feedback/settings` returned `400 Bad Request: property tenantId should not exist`. Root cause: `FeedbackSettingsService` returned the raw `FeedbackSettings` entity (including the newly added, nullable `tenantId` column) from its GET path, and the corresponding PATCH endpoint uses a strict-whitelist DTO (`ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })`). A client that round-trips the full GET response into PATCH gets rejected because `tenantId` is not a declared DTO property.

**Important clarification for the record:** this was **not a defect in the tenant migration strategy**. Stage A's `tenant_id` columns are correctly nullable, additive, and backfilled — no schema or migration decision caused this. It is a **pre-existing, cross-cutting API contract pattern** in this codebase: any controller that returns a raw TypeORM entity via an unfiltered `find()`/`findOne()` (no explicit `select`, no response DTO) is vulnerable to leaking *any* newly added column into a strict-whitelist PATCH round-trip — `tenant_id` simply happened to be the column that exposed it, because it was the next column added to entities that already had this latent gap. The same class of bug would have surfaced from any other additive column change touching these same controllers.

**Scope:** Audited every admin-facing CRUD module introduced/touched in A2–A5 (`system_settings`, `cms_settings`, `license_master`, `license_requests`, `vendor_registrations`, `his_schema_configs`, `users`, `roles`, `permissions`, `password_reset_requests`, `audit_logs`, `notification_logs`, `notification_templates`) for the same pattern: raw-entity GET + strict-whitelist PATCH/PUT.

**Findings:**
- ✅ Safe: `system_settings`, `vendor_registrations`, `his_schema_configs`, `audit_logs` (no controller/HTTP exposure exists for `audit_logs` at all).
- ⚠ Raw entity returned, but no round-trip risk (no corresponding PATCH endpoint, or the write DTO has an unrelated shape): `cms_settings` (PATCH uses an unenforced plain TS type, not a real DTO — flagged as a lower-priority hardening candidate, not fixed here), `license_master`, `license_requests`, `permissions`, `password_reset_requests`, `notification_logs`.
- ❌ Round-trip vulnerability, corrected this checkpoint: `feedback_settings` (fixed prior to this audit being formally scoped), `users`, `roles`, `notification_templates`.

**Fixes applied (all zero-behavior-change outside of no longer leaking `tenantId` in JSON responses):**
- `modules/feedback/settings/feedback-settings.service.ts` — explicit `select` column list on both `findOne()` calls in `_loadFromDb()`, excluding `tenantId`.
- `modules/users/users.service.ts` — `findOne()` strips `tenantId` post-fetch (an explicit `select` array was avoided here because the query uses eager `relations: ['roles', 'roles.permissions', 'directPermissions']`, which a hand-crafted `select` list interacts with less predictably than a straightforward post-fetch `delete`). `findAll()` was already safe — it uses a query-builder `.select([...])` that never included `tenantId`.
- `modules/rbac/roles.service.ts` — `findAll()` and `findOne()` strip `tenantId` post-fetch, same reasoning (eager `relations: ['permissions']`).
- `modules/notifications/notification.service.ts` — `findTemplates()` and `findTemplate()` strip `tenantId` post-fetch.

In every case, the corresponding write path (`update()`/`updateTemplate()`) already used either a targeted `repository.update(id, {...explicit fields})` call or re-fetches via the now-fixed `findOne()` before `save()` — since TypeORM's `save()` omits `undefined`/deleted properties from the generated `UPDATE` rather than writing them as `NULL`, stripping `tenantId` post-fetch cannot cause it to be nulled out in the database. Verified no other consumer of these methods relies on `tenantId` being present on the returned object (Stage A explicitly has no code reading `tenantId` yet — it's unread scaffolding until Stage B).

**Deferred — logged as backlog item "API Contract Cleanup" (not part of this checkpoint, not blocking A6):** `cms_settings`'s ⚠ finding — its PATCH body is a plain `Partial<Omit<CMSSettings,...>>` TS type, not a real class-validator DTO, so `forbidNonWhitelisted` doesn't apply to it at all today. This is a pre-existing DTO gap, independent of tenancy — recommend replacing it with a real decorated DTO class, which incidentally also closes the `tenantId` leak risk on that controller. Not required to unblock A6 since it is not a confirmed round-trip failure today.

**Architectural Lesson:**
- *Lesson:* Adding persistence-only fields to entities can expose API contract weaknesses when controllers serialize entities directly. This was not a defect in the tenant migration — it's a latent pattern that any future additive column (`internalNotes`, `version`, `deletedAt`, `createdBy`, etc.) touching these same controllers would have re-triggered.
- *Recommendation:* Future internal/persistence-only fields should never be returned directly from API responses.
- *Long-term direction:* Replace raw entity responses with dedicated response DTOs across the admin CRUD surface, starting with the controllers touched in this audit; `cms_settings`'s missing PATCH DTO is the most immediate instance of the same underlying gap.

**Roadmap update:** A5.5 (API Contract Audit) is now a permanent, standing checkpoint in the Stage A methodology — not a one-off. It runs after every checkpoint that adds columns to entities with admin-facing CRUD controllers, immediately before the next checkpoint begins: `A5 → A5.5 → A6`, and so on for subsequent batches, not just this one instance.

**Status:** ✅ A5 COMPLETE · ✅ A5.5 COMPLETE · ✅ A6 UNBLOCKED.

## Checkpoint A6 — Platform Modules (AI Platform + Knowledge Search) — DEFERRED (2026-07-14)

**Pre-flight finding:** Of the ~6 conceptual entities originally scoped for A6 (Prompt Templates, Usage, Evaluation Dataset, Traceability, Audit Trail, Knowledge Collection), only 3 are real TypeORM entities (`AiAuditTrailEntity` → `platform_ai_audit_trail`, `AiUsageEntity` → `platform_ai_usage`, `PromptTemplateEntity` → `platform_prompt_templates`), and **none of the three has a migration**. `AiPlatformModule`'s `TypeOrmModule.forFeature([...])` registration is commented out (no repository injected anywhere), and `KnowledgeSearchModule` is not imported into the app module tree at all. The remaining three conceptual entities (`AiTraceabilityEntity`, `EvaluationDatasetEntity`/`EvaluationDatasetRecordEntity`, `KnowledgeCollectionEntity`) are plain TypeScript classes with no `@Entity()`/`@Column()` decorators — not persisted, not migratable.

Confirmed no other blockers exist: no raw SQL, no vector/embedding columns, no object-storage-backed columns, no external AI provider response schema persisted directly (OpenAI/Gemini SDK clients remap into an internal `AiExecutionResult` interface before anything touches persistence), and no controllers/HTTP surface exist yet for either module area. Document Studio / Document Platform (a separate, unrelated subsystem under `modules/document-platform/`) was confirmed out of scope — it was never pulled into the AI Platform / Knowledge Search search and nothing in either module area has a runtime dependency on it. Per standing guidance, scaffold-only or unfinished modules encountered during a pre-flight get a maturity check (exists → maturity level → production dependency check) and then analysis stops — no speculative architecture review.

**Decision:** A6 is **deferred**, not implemented. There is no live table for a nullable `tenant_id` to be added to — the mechanical migration risk is near-zero only because there's nothing to migrate yet. Proceeding as originally scoped would edit TypeScript class shapes with zero database effect, creating a false sense of progress. A6 will be revisited once AI Platform / Knowledge Search actually go live (migrations written, `forFeature` uncommented, controllers added) — at that point it becomes a normal Stage A checkpoint like A1–A5.

**Architectural Lesson:**
- *Lesson:* Not every module named in the original roadmap batching is actually live. A pre-flight review must confirm a table is migrated, registered with TypeORM, and has a real runtime consumer before treating "add a nullable column" as low-risk-and-actionable — "nothing can break" and "nothing needs to be done yet" are different conclusions that look similar from a pure risk-rating lens.
- *Recommendation:* Every future checkpoint's pre-flight should open with an entity-persistence confirmation (real `@Entity()`, has a migration, has `forFeature` registration, has at least one consumer) before deep-diving into column-level analysis — this would have shortened A6's investigation.
- *Long-term direction:* Track "scaffolded but not live" modules (AI Platform, Knowledge Search, Document Platform) in a lightweight backlog list so future checkpoint planning doesn't need to rediscover their state from scratch each time.

**Revised checkpoint risk outlook (forward-looking, not yet executed beyond A6):** A7 Loyalty 🟢 Low · A8 EIC 🟡 Medium · A9 Attendance 🟡 Medium · A10 Document Platform/Studio ⚪ Deferred/Incomplete (same reasoning as A6, pending client requirements) · A11 CMS 🟡 Medium · A12 Feedback 🟡 Medium · A13 Token 🔴 High (Oracle integration, sequences, realtime operations, raw SQL — most critical remaining checkpoint).

**Status:** ⚪ A6 DEFERRED. Proceeding to A7 pre-flight.

## Phase 3 — Storage Providers: Complete (sandbox-reachable scope)

**Date:** 2026-07-15
**Companion doc:** `PHASE_3_IMPLEMENTATION_PLAN.md`

Following the "proceed to phase 3" directive, a pre-flight re-read of Phase 2's storage abstraction confirmed `IObjectStorageProvider`'s shape needed no changes, `StorageModule` had no mode-selection logic yet, and `ObjectRepositoryService.storeFile()` had no `tenantId` parameter — exactly matching the three roadmap tasks. One new finding not previously flagged: `TokenController.listMedia()`/`deleteMedia()`, `CmsMediaController.permanentDelete()`, and `CmsAssetCleanupService`'s delete path all gate on raw `fs.existsSync()`/`fs.readdirSync()` against local disk rather than going through the storage abstraction — under `STORAGE_DRIVER=s3` these will misbehave (list always empty, delete always 404s) until a follow-up adds a `list()`/existence-check method to the interface. Deliberately not fixed in this pass (materially larger than Task 3.3's write-path scope); logged as a follow-up, not silently left broken.

**Task 3.1 — S3StorageProvider:** new file at `platform/services/object-repository/providers/s3-storage.provider.ts`, implementing `IObjectStorageProvider` via `@aws-sdk/client-s3` + `@aws-sdk/lib-storage` (multipart-safe upload, doesn't break above S3's 5GB single-PUT limit) + `@aws-sdk/s3-request-presigner`. Added the three `@aws-sdk/*` packages to `backend/package.json` — version pins need confirming via a real `npm install`, since this sandbox can't reliably query the npm registry. Added `STORAGE_DRIVER` (`local`/`s3`, default `local`) plus `S3_BUCKET`/`S3_REGION`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` (required only when `STORAGE_DRIVER=s3`, via Joi `.when()`) and optional `S3_ENDPOINT`/`S3_FORCE_PATH_STYLE` (MinIO/R2-style endpoints) to `src/config/env.validation.ts`.

**Task 3.2 — StorageModule mode-selection:** both `LocalStorageProvider` and `S3StorageProvider` are now always registered (cheap — `S3StorageProvider`'s constructor only builds an `S3Client`, no eager connection); a new `STORAGE_PROVIDER` factory reads `STORAGE_DRIVER` via `ConfigService` and selects one. Unset/`'local'` is byte-for-byte Phase 2's original wiring — zero behavior change for every current deployment.

**Task 3.3 — tenant-prefixed object keys:** `IObjectStorageProvider.upload()` and `ObjectRepositoryService.storeFile()` both gained an optional `tenantId?: string | null` parameter. `LocalStorageProvider` ignores it (local deployments are single-tenant-per-install today). `S3StorageProvider` uses it as a `<tenantId>/<subdir>/<filename>` key prefix when present, falling back to the unprefixed key when absent. The three real upload call sites (`CmsMediaController.upload`, `TokenController.uploadMedia`, `FeedbackFormController`'s upload handler) now inject `TenantContextStorage` (the same B6-established helper class) and resolve `tenantId` via `currentTenantIdOrNull()` before calling `storeFile()`. Null-safe by construction — routes without an established ambient tenant context (e.g. `TokenController.uploadMedia`, which doesn't currently carry `TenantContextInterceptor`) simply get `null` and behave exactly as before.

**CI:** added `s3-storage.provider.ts` to Task 2.9's infrastructure-import-boundary guardrail's `PROVIDER_FILES` list (no binding-module allow-list change needed). Added a gated S3 conformance suite (`s3-storage-provider.conformance.spec.ts`, skipped everywhere `RUN_S3_CONFORMANCE_TESTS` isn't `'true'`) covering upload/download round-trip, tenant-prefix vs. no-prefix key shape, metadata accuracy, idempotent delete, and presigned-URL generation — and a new `storage-s3-conformance` CI job that brings up a MinIO service container and runs it, kept separate from the main `backend` job so a MinIO flake can't fail everyone else's build.

**Deliberately not attempted:** Task 3.4 (piloting `STORAGE_DRIVER=s3` in a real staging environment) — same environment-dependency posture as every prior phase's production-gated item. The four fs-based list/delete call sites identified in the pre-flight — logged as a real, separate follow-up, not folded into this pass.

**Follow-ups for a human:** run `npm install` to lock the new AWS SDK version pins; run the real toolchain's build/test/lint (this sandbox's checks remain non-authoritative per every earlier phase's standing note); migrate the four fs-based list/delete call sites off raw `fs` once `IObjectStorageProvider` gains a `list()`/existence-check method; pilot Task 3.4 in staging once available.

**Follow-ups for a human:** lock the two new AWS SDK package pins via `npm install`; run the real build/test/lint toolchain; consider a LocalStack-backed live SES/SNS conformance suite before any real deployment sets `cloud` mode; `sendPush()` has no wired queue call path yet (needs a `PUSH` `NotificationChannel` value + processor case + a real push backend in at least one provider); cross-provider fallback (`retryable: true` driving cloud->local failover) is documented but not implemented.

## Phase 7 — Cloud Oracle Transport: Complete (sandbox-reachable scope)

**Date:** 2026-07-16
**Companion docs:** `PHASE_7_VENDOR_PORTAL_IMPACT_ANALYSIS.md` (preceding cross-repo analysis, user-confirmed: no Vendor Portal changes needed), `PHASE_7_IMPLEMENTATION_PLAN.md`

User directed Phase 7 to mirror the Interface → Second Provider → Configuration Switch pattern from Phases 3-5 exactly, with one added invariant: Business modules (HIS, Attendance, EIC, Token, Loyalty) must never know whether Oracle is local or remote.

**The one real design question Phase 7 had to resolve:** `IOracleTransport.query()`/`execute()` take an arbitrary raw SQL string, but Phase 6's Message Transport only accepts a pre-registered `sqlTemplateId` (a deliberate security boundary, not a Phase 7 shortcut to work around). This means `CloudOracleTransport` today only supports the one conformance/pilot query registered so far (`SELECT 1 FROM dual`) — expanding to real production HIS queries is explicitly deferred, matching the user's own success criterion ("Connector successfully executes allow-listed SQL templates," not "arbitrary raw SQL parity").

**Task 7.1:** `CloudOracleTransport` (`backend/src/modules/his/cloud-oracle.transport.ts`) implements `IOracleTransport` via `@hdsp/connector`'s `RedisMessageTransport` (backend now depends on `@hdsp/connector`, mirroring Phase 6's `@hdsp/oracle-client` wiring). A response with `error.retryable: true` maps to a thrown `HisUnavailableError` — the same exception type `OracleClient` throws — so every existing Business-module catch block keeps working unchanged.

**Task 7.2:** `his-config.module.ts`'s `ORACLE_TRANSPORT` binding is now a mode-selection factory (`direct`/`cloud_relay`, default `direct`), identical pattern to Phases 3-5. New env vars: `ORACLE_TRANSPORT`, `CONNECTOR_REDIS_URL`, `CONNECTOR_REQUEST_TIMEOUT_MS`.

**Task 7.3:** mocked conformance suite (ioredis mocked at module level, no live Redis/Oracle) proving same-shape results for the shared conformance query, the deliberate allow-list divergence for non-registered queries, and `HisUnavailableError` mapping parity.

**Task 7.4:** same cooldown-based circuit breaker as `OracleClient`, tripped only by transport-level failures. One documented, deliberate non-parity: no per-query retry on `CloudOracleTransport` (unlike `OracleClient`'s pool-creation retry) — retrying a `send()` that may have already reached the Connector risks duplicate execution of a non-idempotent template, a risk `OracleClient`'s connect-time-only retry never had.

**Explicitly not attempted:** Task 7.5's real pilot — requires a deployed Connector instance, real test Oracle, and real Redis, none available in this sandbox. **Two real gaps found and fixed, not just infrastructure written on faith:**
1. ## B3.1 Pre-Flight — Audit Removed From B3, Scoping Rule Established (2026-07-14)

**Finding:** investigated Audit and Notification's actual read/write architecture before wiring anything. `audit_logs` has no HTTP surface at all — `AuditService.log()` only enqueues a BullMQ job (`audit.service.ts`); `AuditProcessor` (`audit.processor.ts`, a `@Process('write-audit-log')` handler) performs the actual `auditRepo.save()` on a worker, with no `AuditController` and no `GET` endpoint anywhere (consistent with the A5.5 finding already on record). By the time the worker runs, the original HTTP request's `AsyncLocalStorage` context (which `TenantContextInterceptor` would have populated) no longer exists. `NotificationController`, by contrast, is a synchronous, `JwtAuthGuard`-protected controller with real `GET` endpoints on `NotificationLog`/`NotificationTemplate` — the exact shape B3's mechanism was designed around.

**Scoping rule established (not a one-off exception):** B3 covers read-side tenant enforcement on request-scoped code paths only. Any module whose persistence occurs exclusively inside an asynchronous worker (Bull/BullMQ `@Process()`, `@Cron()`) bypasses B3 and is implemented in B6, because request-scoped tenant context is unavailable once work leaves the HTTP pipeline. Audit is the first confirmed example of this rule, not a special case — any future module discovered to be background-only during its own B3.x pre-flight follows the same path. `STAGE_B_IMPLEMENTATION_PLAN.md`'s B3 and B6 sections both state the rule explicitly, not just "Audit moved to B6."

**Decision:** B3.1 is Notification only (`notification_logs`, `notification_templates`). Audit moves to B6, where its tenant must be resolved and captured explicitly at job-enqueue time (inside the still-live request context) and carried through the job payload — the worker cannot rely on ambient `AsyncLocalStorage` the way a request-scoped repository call can.

**B3.1 designated the reference implementation for every subsequent Pattern 1 module**, with an explicit 7-step success sequence recorded in the implementation plan: dry-run both repositories → exercise all four `GET` endpoints → confirm clean dry-run logs (tenant detected, would-filter counts, zero unexplained mismatches) → flip to enforced → repeat the same endpoints → verify identical results → only then proceed to B3.2. Every later B3.x module repeats this same sequence rather than each one inventing its own verification shape.

**Status:** ✅ Pre-flight complete · ✅ Scoping rule + module split documented in both governance docs · ➡️ Ready to implement B3.1 (Notification): wire `TenantContextInterceptor` on `NotificationController`, construct dry-run `TenantScopedRepository` instances for `NotificationLog`/`NotificationTemplate`.

## Bug Fix — `TenantScopedRepository` Ignored `mode: 'dry-run'` Outside `find()`/`findAndCount()` (2026-07-14)

**Reported symptom (live, office environment):** creating a new user via `POST /api/v1/users` returned `404 Not Found: User <id> not found` immediately after a successful insert. Clicking Save again then returned `409 Conflict: username already exists` — proving the first request's INSERT had actually succeeded; only the response after it failed.

**Root cause:** `TenantScopedRepository.find()` and `.findAndCount()` correctly check `this.mode === 'dry-run'` before applying the enforced tenant predicate (built that way from the start, since B2). Every other method — `findOne()`, `findOneBy()`, `findBy()`, `count()`, `exist()`, `createQueryBuilder()`, `update()`, `delete()`, `softDelete()` — never checked `this.mode` at all and unconditionally applied the enforced `tenant_id = <current tenant>` predicate, regardless of whether the provider was configured with `mode: 'dry-run'` or `mode: 'enforced'`. This was a defect in B2's original implementation, invisible until B3.3 was the first checkpoint to route a write-adjacent read (`UsersService.create()` calling `this.findOne(saved.id)` right after `save()`) through a `findOne()` on a `dry-run`-mode provider.

Because Stage B write-path tenant stamping is explicitly deferred to B6 (not yet implemented — a deliberate, documented B2 design decision), every row inserted today still has `tenant_id = NULL`. `UsersService.create()` saves the new user via the raw repository (write paths were never converted, per the B3.3 boundary), then calls `this.findOne(saved.id)`, which now routes through `scopedUserRepo.findOne(...)`. Despite `users.module.ts` configuring `User` with `mode: 'dry-run'` specifically so this rollout phase would be zero-behavior-change, the bug made `findOne()` enforce anyway — filtering `WHERE tenantId = 'default'` against a row whose `tenantId` is `NULL`. No match, `findOne()` returns `null`, `UsersService.findOne()` throws `NotFoundException`, and the client sees `404` even though the insert committed. Retrying then collides on the unique username/email constraint → `409`.

This same latent bug also affected `UsersController.findAll()` (via `createQueryBuilder()`, also unconditionally enforced) and any RBAC/Auth read routed through the newly-added scoped repositories in B3.3 — any of them could have hidden legitimately-visible rows the instant a provider was meant to be in inert dry-run mode.

**Fix:** every method in `tenant-scoped.repository.ts` now checks `this.mode` before enforcing, mirroring the pattern `find()`/`findAndCount()` already used. Added five new private dry-run counterparts — `findByDryRun()`, `findOneDryRun()`, `findOneByDryRun()`, `countDryRun()`, `existDryRun()` — each running the real unfiltered/unscoped query (zero behavior change) and separately logging what the enforced result would have been (`warn` on mismatch, `debug` otherwise), same shape as the existing `findDryRun()`/`findAndCountDryRun()`. `createQueryBuilder()` now returns an unscoped builder under `mode: 'dry-run'` (only a debug log fires — no per-row comparison query, since an arbitrary query builder can't be counted generically). `update()`/`delete()`/`softDelete()` now pass criteria through unscoped under `mode: 'dry-run'`, with a debug log noting the bypass (no separate before/after comparison for writes — out of scope, and these three methods have zero real callers today since B3.3 kept all writes on raw repositories).

**Regression tests added** to `tenant-scoped-repository.spec.ts` (9 new cases, one per previously-unguarded method) — the key one constructs a row with `tenantId: null` (simulating a freshly-inserted, not-yet-B6-stamped row) and asserts `findOne()` in dry-run mode still returns it unfiltered. Full suite: 20/20 passing. The canonical cross-tenant isolation test (`tenant-enforcement-canonical.spec.ts`) was also re-run and still passes 5/5 — that test exercises `mode: 'enforced'` exclusively, which was never broken; this bug was specific to `mode: 'dry-run'` being silently ignored outside two methods.

**Scope of impact:** every module currently in `mode: 'dry-run'` — `User` (B3.3), `Role`/`Permission` (B3.3), `PasswordResetRequest` (B3.3) — was exposed to this bug the moment any of their converted methods ran against a row without a populated `tenant_id` (which is every row today, since B6 hasn't run). `NotificationLog`/`NotificationTemplate` (B3.1) are in `mode: 'enforced'` already and were never in scope for this specific bug, though the same underlying gap existed in the code the whole time — it simply had no `dry-run`-mode consumer exercising `findOne`/`createQueryBuilder`/etc. until B3.3.

**Corrective action for the standing verification runbook:** the B3.1-derived 7-step runbook (dry-run → review logs → flip to enforced → re-verify) is now the *only* way this class of gap gets caught before enforcement — this incident is the reason it exists. B3.3's verification pass, not yet run, must specifically confirm no `MISMATCH` warnings appear across `findOne`/`findOneBy`/`findBy`/`count`/`exist`/`createQueryBuilder` for `User`/`Role`/`Permission`/`PasswordResetRequest`, in addition to the standard `find`/`findAndCount` checks already covered by the runbook template.

**Status:** ✅ Fixed and unit-tested. Not yet verified against the real office environment — folded into B3.3's still-pending verification runbook above.

## Governance Update — B3 Eligibility Rule Formalized (2026-07-14)

**Trigger:** B3.4's pre-flight review observation — B3.1 (Audit), B3.2 (Licensing), and B3.4 (Loyalty) each independently rediscovered the same underlying boundary through three separate investigations. B3.4 in particular showed the rule operating *within* a single module for the first time (3 of 11 read methods on the same entities excluded, 8 converted) rather than excluding a module wholesale, which is what made the pattern precise enough to state as one rule instead of two separate scoping notes.

**The rule, added to `STAGE_B_IMPLEMENTATION_PLAN.md`'s B3 section:** a repository read method is eligible for B3 conversion only if it (1) is invoked exclusively from request-scoped HTTP controllers, (2) never executes from `@Cron`, a BullMQ worker, a CLI command, a seed script, or startup logic, (3) does not participate in a write workflow, and (4) does not require system-scope bypass. Eligible reads go to `TenantScopedRepository` under B3; anything failing the test stays on the raw repository and is handled under B6 (or, per B3.2, left as an explicitly-open question when the cross-cutting consumers are themselves HTTP-scoped rather than purely background).

**Effect:** this rule now explains B3.1's whole-module exclusion (fails test 1/2), B3.2's whole-module deferral (fails test 1), and B3.4's per-method split (fails test 2/3 for 3 of 11 methods) without treating any of them as a one-off exception. It supersedes the two separately-stated scoping rules from B3.1 (async-worker) and B3.2 (cross-cutting-consumer) — both are now subsumed as specific instances of this one test — though those entries remain in the log unedited as the historical record of how the rule was derived.

**Standing instruction:** every remaining B3.x pre-flight (B3.5 EIC, B3.6 CMS, B3.7 Token, B3.8 Feedback) applies this four-part test directly rather than re-deriving module-specific reasoning from scratch.

## Governance Update — Eligibility Rule Re-Centered on Resolver Availability, Not "HTTP Request-Scoped" (2026-07-15)

**Instruction, in response to the CMS pre-flight's test-1 gap:** replace "every call site executes within the same request-scoped HTTP context" with **"every call site executes in a context where a tenant can be deterministically resolved using the resolver strategy assigned to that context, and that strategy is `SessionTenantResolver`."** The distinguishing question stops being "is this HTTP" (anonymous player requests are technically HTTP too, which is exactly what made the old wording insufficient) and becomes "does this context have a resolver that gets the right answer."

**Execution Context Classification, revised to name contexts by their resolver rather than their historical discovery order:**

| Context | Resolver | Stage |
|---|---|---|
| Authenticated HTTP (`request.user` carries a principal) | `SessionTenantResolver` | B3 |
| Anonymous/public HTTP (slug, token, branch param, etc.) | `ChainTenantResolver` | B5 |
| Oracle/HIS-derived execution | `OracleTenantResolver` | B4 |
| `@Cron` / BullMQ `@Process` / detached async / CLI / startup / seed | explicit captured tenant or `runAsSystem()` | B6 |

**Terminology change, explicit and permanent:** what B3.6 initially proposed as "PUBLIC/ANONYMOUS — Pattern 3" is renamed **Chain-resolved execution (B5)** — not a temporary bucket but a first-class architectural category, on par with session-resolved, Oracle-resolved, and system/background. Every pre-flight from B3.6 onward uses this vocabulary directly; B3.1–B3.5's existing write-ups are not retroactively relabeled since their findings are unchanged, only the terminology going forward is.

**CMS classification approved as originally proposed, under the renamed categories:** 22 methods → B3 (session-resolved), 13 → B5 (chain-resolved, was "Pattern 3"), 2 → B6 (system/background). `CmsSettingsService.get()` stays fully raw rather than split, since it has both a chain-resolved and a system/background call site in addition to its session-resolved one — matching the explicit instruction that a method reachable from more than one non-B3 context doesn't get partially converted.

**Assessment (user's, recorded for future reference):** this is treated as one of the more significant architectural discoveries of Stage B, on par with B2's `TenantScopedRepository` design — it simplifies governance by making every future B3.x/B4/B5/B6 classification a single question (which resolver, if any, is available in this context) instead of a growing list of module-specific exceptions. The 22/13/2 distribution across B3/B5/B6 is noted as evidence the rule isn't being applied either too aggressively (most things landing in B3) or too conservatively (most things landing in B5) — a roughly two-thirds/one-third split between session-resolved and chain-resolved reads, consistent with CMS's shape as a module that is both an authenticated admin tool and a public content server.

**Status:** ✅ Adopted. B3.6 implementation proceeds using only the 22 session-resolved methods; every chain-resolved read stays on the raw repository until B5 introduces `ChainTenantResolver`.

### Tenant-Scoped User Identity — Task 8 (HIS webhook contract: add tenant identifier) implemented (2026-07-17)

Pre-flight research (a dedicated investigation, same discipline as every other task this session) traced the full call chain before touching any code, and it changed this task's shape from "coordinate a contract change with an external system" to "close a real but currently-latent gap, safely, with no external coordination actually available yet." Findings: `applyHdspUsers()` has exactly one caller in this repo, `LicenseController.vendorWebhook()`'s `HIS_CONFIG_UPDATE` branch, authenticated by manual HMAC-SHA256 (`X-Vendor-Signature`, keyed by a per-hospital `instanceSecret`) rather than any JWT/subdomain path -- meaning `SubdomainTenantMiddleware`'s `req.tenantId` was never a usable source of tenant identity here in the first place, since self-hosted webhook deliveries hit a bare `publicIp:publicPort` URL that `extractSubdomain()` can never resolve to a real subdomain. Second, and the finding that actually determined this task's scope: the only sender that exists anywhere in this codebase, `HospitalsService.pushHisConfigWithUsers()` in `vendor-portal/backend`, exclusively targets the self-hosted `Hospital` entity. `CLOUD_TENANT_ONBOARDING_DESIGN.md`'s own documented topology confirms self-hosted deployments are single-tenant by construction (one isolated backend + DB per hospital, seeded with exactly the 'default' tenant), and a direct grep of the `cloud-tenants/` module found zero references to `WebhookService`, `deliver()`, or `hdspUsers` -- `CloudTenant` (the multi-tenant SaaS entity) has no HIS-sync feature built at all yet, and `WebhookService.deliver()`'s signature is nominally typed to `Hospital` specifically, so a `CloudTenant` couldn't even structurally be passed to it today.

**Conclusion this pass acted on:** the mis-tenanting risk the plan's write-up warned about is real but latent, not a live incident -- every confirmed-live caller already has exactly one tenant, so stamping to 'default' was already the correct end state for it. The actual risk is that a *future* cloud HIS-sync feature would inherit this same code path and silently mis-tenant users the day it's built, with no payload field available to prevent it. So this task shipped as a forward-compatible, zero-behavior-change-for-self-hosted contract hardening rather than a cross-system coordination effort: `VendorWebhookDto` gained an optional `tenantId` (`@IsUUID()`, validated), threaded from `LicenseController.vendorWebhook()` into a new `applyHdspUsers(users, tenantId?)` second parameter. A new `resolveTargetTenant()` helper resolves either the supplied `tenantId` -- validated against the real `Tenant` table, with an unresolvable UUID aborting the entire batch (logged, not thrown past the caller) rather than silently falling back to 'default', since a silent fallback on a bad tenant UUID would be strictly worse than failing loudly -- or the seeded 'default' tenant when `tenantId` is omitted, byte-identical to pre-Task-8 behavior for the only live caller. The existing-user upsert lookup, previously a bare `{ username }` (already stale the moment Task 5 shipped composite `(tenantId, username)` uniqueness earlier this session, though not yet fixed until now), is now `{ username, tenantId: targetTenant.id }` -- closing a real latent bug where this lookup could otherwise have found and silently overwritten a *different* tenant's same-named user once any tenant besides 'default' existed. New-user placeholder emails: unchanged (`${username}@hdsp.local`) on the 'default'-tenant path to avoid altering production email values for the only live caller for zero benefit; tenant-qualified (`${username}@${tenantCode}.hdsp.local`) only when a real non-default `tenantId` is supplied, addressing the plan's explicit call to "stop synthesizing emails without a tenant-qualified username to build them from." No Vendor Portal-side sender change was made, since none exists yet needing one -- but the stable cross-system identifier a future cloud sender would use was confirmed via a second research pass: `CloudTenant.hdspTenantId` already stores the exact HDSP `Tenant.id` UUID (`cloud-tenants.service.ts`'s post-provisioning save), so a future `CloudTenant`-facing HIS-sync feature has a ready-made, already-correct value to pass as `tenantId` from day one.

Real `tsc`/`jest` still not completable in this sandbox (same standing limitation since Task 3); the usual recommendation to run the real toolchain before deploying applies here too, though this task's blast radius is smaller than Task 5's -- it's additive (`tenantId` optional, unused by any live caller) rather than a schema-level constraint change.

### CMS Displays incident — missing-interceptor tenant-stamping bug, module-wide sweep, and hardening (2026-08-07)

**Trigger:** a live report — `app.zoeconnect.in/cms/displays` showed "No displays registered yet" after clicking "+ New Display," and retrying with the same name returned HTTP 409.

**Root cause, traced controller → service → repository → back to the list query:** `CmsDisplayController.create()` (`POST /cms/displays`) had no `@UseInterceptors(TenantContextInterceptor)`, unlike its sibling routes on the same controller. `CmsDisplayService.create()` calls `TenantContextStorage.currentTenantIdOrNull()` to stamp the new row's `tenantId`; with no context established, this silently resolved `null` rather than throwing. The row **was** inserted, with `tenant_id = NULL`. `list()` (which does carry the interceptor) queries through `TenantScopedRepository`, which merges `{ tenantId: <real tenant> }` into every `find()` — a real tenant UUID never equals `NULL` in SQL, so the row was invisible to every subsequent list call. The 409 on retry came from `create()`'s own slug-uniqueness pre-check, which uses the raw (unscoped) repository and so could still see the orphaned row by slug.

**Same pattern found and fixed at three more sites** via a full sweep of `backend/src/modules/cms/**`'s ten controllers, then a repo-wide grep of all 111 `currentTenantIdOrNull()` call sites, then a second, multi-hop-aware pass specifically checking for the write-stamping call living 2+ service layers below an uninstrumented controller (a shape a direct-caller grep alone would miss):

1. `CmsTickerController.create()` (`POST /cms/displays/:displayId/ticker-messages`) — same gap. Manifested differently: `listForDisplay()` is unscoped, so new messages were listable, but `update()`/`remove()` go through the scoped `findOne()`, so a `tenant_id = NULL` message could be seen but never edited or deleted (404).
2. `DisplayController.create()` (Token module, `POST /token/display-pages`) — structurally identical to the CMS Displays bug, including the same raw-repo slug-conflict check.
3. `TokenConfigController`'s `POST`/`PUT /token/config/sc-configs` (`upsertScConfig()`) — the first SC config created per branch was invisible to the scoped `listScConfigs()`.
4. `CmsSettingsController` — found by the multi-hop audit, not the direct-caller grep: the controller has no interceptor at all, and while `update()` doesn't call the tenant-stamping method itself, it reaches `CmsAuditService.log()` two hops down (`CmsSettingsService.update()` → `auditService.log()`), which does. Every CMS settings change's audit-trail row was silently persisted with `tenant_id = NULL`, invisible to `listRecent()`/`listForEntity()`. `CMSSettings` itself is a deliberate global singleton (see its own entity comment), so this was an audit-trail visibility gap, not a cross-tenant data leak — but the identical missing-interceptor shape.

Fixed all four by adding `@UseInterceptors(TenantContextInterceptor)` to the affected routes (method-level for the mixed public/admin controllers — CMS Displays, CMS Ticker, Token Config; class-level for `CmsSettingsController`, whose routes are uniformly authenticated admin routes).

**Explicitly investigated and NOT changed — `TokenConfigService.getBranding()`** (`GET /token/config/branding`, `@Public()`). Lazy-creates a branding row on first hit and stamps the same `currentTenantIdOrNull()`-derived `tenantId`, but this route has no session/JWT at all (anonymous kiosk board), so `TenantContextInterceptor` has nothing to resolve from `request.user` even if applied. Doesn't reproduce the invisible-row symptom either — both `getBranding()`/`updateBranding()` look the row up by `branchId` on the raw (unscoped) repository, not a tenant-scoped one — so this is an orphaned-data hygiene issue, not a functional bug. Needs a different mechanism (resolving tenant from `branchId`, the same way the workstation/capability-token chain resolver already does elsewhere) — left as a separate follow-up, not bundled into this pass.

**Hardening — new `TenantContextStorage.requireTenantContext()`** (`tenant-context-storage.ts`): a fail-fast counterpart to `currentTenantIdOrNull()` for write paths where a `null` tenantId is always a bug, never a valid state. Wraps the existing (already-throwing) `currentTenantId()` and converts its error into a clear `InternalServerErrorException`. Deliberately **not** a global replacement — `currentTenantIdOrNull()` remains correct for its many legitimate callers (background jobs, `runAsSystem()` call graphs). Applied narrowly, at the exact five write sites this incident touched: `CmsDisplayService.create()`, `CmsTickerService.create()`, `DisplayService.create()` (Token), `TokenConfigService.upsertScConfig()`'s new-row branch, and `CmsAuditService.log()` (the last one safely, since `log()` already wraps everything in a try/catch that must never break the primary operation — a missing context there now skips the audit row instead of corrupting it).

**Multi-hop bypass audit (read-only, no findings beyond the four above):** re-walked the call graphs of the largest tenant-context consumers (incident module's 8 sibling services off `IncidentService`/`IncidentTimelineService`, CMS's `CmsAuditService` fan-in from 9 callers, Token's `WorkstationController`) specifically looking for a service method reachable from two or more controllers where only one caller carries the interceptor. Found the `CmsSettingsController` gap (folded into the fixes above); everything else traced back to either a controller with class-level coverage regardless of hop depth (`AsyncLocalStorage` context follows the request, not the direct caller, so hop depth alone isn't a risk factor once *a* covering interceptor sits anywhere upstream in that request's call chain) or a deliberately different, already-correct tenant-resolution mechanism (`ChainTenantResolver` for public kiosk/workstation flows; `CmsAssetCleanupService`'s explicit `TenantContextStorage.run()` wrapping for its own per-row system-scope cleanup).

**Cleanup — orphaned rows from before this fix** (inspect before acting; no blind migration, since a `NULL`-tenant row's correct tenant can't be safely inferred from `branchId` alone):

**Deferred follow-up — CI safeguard (not implemented this pass, scoped intentionally out):** the review that closed this incident recommended a semantic check rather than a decorator-presence check — *"any controller endpoint that writes to a tenant-scoped repository must execute inside an established tenant context,"* deliberately not tied to `TenantContextInterceptor` by name, since a future change could establish context another way. An ESLint custom rule can't reason about cross-file call graphs or async control flow cheaply; the more realistic mechanisms are (a) an architecture/static-analysis test (e.g. a script using the TypeScript compiler API to walk each controller route's call graph, flag any reachable `TenantScopedRepository` write or `requireTenantContext()`/`currentTenantIdOrNull()` call not provably inside an interceptor-covered path) or (b) an integration test that boots the app, calls every mutating route without any tenant-establishing mechanism stubbed differently per route, and asserts a consistent pass/fail against a maintained allowlist. Neither was built this pass — this entry exists so the next person picking this up doesn't have to re-derive the incident's context.
