# ADR-015: Platform Boundaries — Designer API vs. Runtime API, dynamic-forms as Consumer

**Status:** Accepted (Frozen — Phase 1–6 roadmap approved 2026-07-05)

## Context

Designer traffic (low volume, high payload complexity, strict RBAC) and Runtime traffic (high volume, latency-sensitive, resolved-schema-only) have different operational characteristics; and dynamic-forms as a module must not silently re-absorb responsibilities that belong to the Document Platform.

## Decision

Routes are partitioned into /forms/designer/... and /forms/runtime/... namespaces, both served by application services in dynamic-forms that delegate to Document Platform services (Document Engine, Workflow Engine, Notification Engine, Resolver, Rule Engine, Variables Engine, Theme Engine, Asset Library) for every cross-cutting concern. Controllers stay thin (HTTP concerns only); no controller or application service reimplements versioning, workflow, or notification logic itself.

## Consequences

Caching, rate-limiting, and RBAC policy can differ cleanly between the two namespaces. Any future second Application (Consent Forms, etc.) can reuse the identical platform services dynamic-forms already proved out. Trade-off: this discipline must be enforced by code review (Phase 4B §9.1) since NestJS will not itself prevent a shortcut.
