# ADR-012: Security Model — RBAC, Audit, and Server-Side Re-Validation

**Status:** Accepted (Frozen — Phase 1–6 roadmap approved 2026-07-05)

## Context

A form platform touching patient data needs field/section/form-level access control and a complete change history, without inventing a parallel authorization or audit system alongside HDSP's existing one.

## Decision

Reuse HDSP's existing JWT + refresh + Redis blacklist auth, RolesGuard/PermissionsGuard with MODULE:RESOURCE:ACTION keys (namespaced FORMS:*), and AuditService/@Audit convention for every template and submission change. The client-side rule engine's visibility/permission decisions are always re-validated server-side on submit — the client is never trusted alone. Rule and variable expressions are closed, non-executable JSON expression trees (no eval/new Function), eliminating a major injection surface by construction.

## Consequences

No parallel security system to keep in sync with HDSP's evolving RBAC. Field-level permission bypass attempts fail server-side even if a compromised/modified client sends otherwise. Trade-off: the rule/variable engine's function set is deliberately closed and enumerable — new rule capabilities require extending the closed set, not adding arbitrary scripting.

## Source

Phase 1 §5.3, §5.4; Phase 2 §3.3; Phase 4B §1 (thin controllers delegating to guarded application services).
